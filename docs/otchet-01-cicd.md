## 1. CI/CD

### 1.1. Цель и критерии этапа

В соответствии с требованиями трека DevSecOps (Нетология) на этапе CI/CD (*Continuous Integration / Continuous Delivery* — непрерывная интеграция и доставка) необходимо:

1. настроить пайплайн сборки и доставки программного обеспечения;
2. использовать облачные сервисы для развёртывания артефактов;
3. задокументировать процесс.

В рамках дипломной работы реализована **автоматическая сборка Docker-образов** backend и frontend Necommerce при каждом изменении кода в ветке `main`, а также **публикация образов** в облачный реестр **GitHub Container Registry (GHCR)**. Развёртывание на выделенный **VPS** (виртуальный сервер) запланировано на последующем этапе работы; на момент описания данного раздела конвейер обеспечивает сборку и хранение образов в облаке GitHub.

### 1.2. Выбор платформы

Для организации CI/CD выбрана платформа **GitHub Actions** — встроенный в GitHub механизм автоматизации, запускающий сценарии (*workflow*) на виртуальных машинах (*runners*) при событиях `push` и `pull_request`.

**Обоснование выбора:**

| Критерий | GitHub Actions |
|----------|----------------|
| Интеграция с репозиторием | Код и пайплайн в одном месте |
| Стоимость | Бесплатные минуты для публичных репозиториев |
| GHCR | Единая экосистема: код → сборка → реестр образов |
| Документирование | История прогонов в интерфейсе Actions |

Альтернативы (GitLab CI/CD, CircleCI) в задании указаны как рекомендуемые; GitHub Actions выбран как наиболее прямой вариант при размещении исходного кода на GitHub.

**Репозиторий диплома:** https://github.com/softm-bot/necommerce-devsecops

### 1.3. Архитектура пайплайна

Конфигурация пайплайна описана в файле `.github/workflows/ci.yml`. При отправке изменений в ветку `main` GitHub запускает workflow **«CI — Docker build & GHCR»**, в котором **параллельно** выполняются два задания (*job*):

| Job | Каталог сборки | Результат |
|-----|----------------|-----------|
| **Backend — сборка и GHCR** | `necommerce-backend/` | Docker-образ JAR-приложения Spring Boot |
| **Frontend — сборка и GHCR** | `necommerce-frontend/` | Docker-образ статики React за nginx |

Общая схема:

```
push / pull_request → ветка main
        ↓
   GitHub Actions (runner: ubuntu-latest)
        ↓
   ┌────────────────────┬─────────────────────┐
   │ checkout кода      │ checkout кода       │
   │ docker build       │ docker build        │
   │ push → GHCR        │ push → GHCR         │
   │ (только при push)  │ (только при push)   │
   └────────────────────┴─────────────────────┘
        ↓
ghcr.io/softm-bot/necommerce-backend:latest
ghcr.io/softm-bot/necommerce-frontend:latest
```

**Триггеры:** `push` и `pull_request` в ветку `main`.

**Публикация в GHCR** выполняется только при событии `push` (не при pull request), чтобы не засорять реестр промежуточными сборками.

### 1.4. Этапы внедрения

Работа над CI/CD выполнялась поэтапно.

#### 1.4.1. Минимальный CI (проверка сборки)

На первом подэтапе в workflow задано `push: false` — образы собирались на runner GitHub, но **не публиковались**. Цель — убедиться, что Dockerfile backend и frontend корректны и проект собирается в чистой среде CI.

*→ Рис. 4. GitHub Actions — успешный прогон сборки Docker (оба job в статусе Success)*

#### 1.4.2. Публикация в GHCR

На втором подэтапе добавлены:

- шаг **Login в GHCR** (`docker/login-action`);
- параметр `push: true` при push в `main`;
- теги образов: `latest` и уникальный тег по хешу коммита (`github.sha`).

**Адреса опубликованных образов:**

- `ghcr.io/softm-bot/necommerce-backend:latest`
- `ghcr.io/softm-bot/necommerce-frontend:latest`

Для аутентификации в GHCR в настройках репозитория GitHub создан секрет **`GHCR_TOKEN`** (Personal Access Token с правами `repo`, `workflow`, `write:packages`). Токен не хранится в исходном коде.

*→ Рис. 5. GitHub Packages (GHCR) — опубликованные контейнеры necommerce-backend и necommerce-frontend*

*→ Рис. 6. Фрагмент файла `.github/workflows/ci.yml` в репозитории*

### 1.5. Корректировка Dockerfile

При первых прогонах пайплайна сборка завершилась с ошибкой. Анализ логов GitHub Actions выявил две независимые проблемы в исходных Dockerfile проекта Necommerce:

| Компонент | Проблема | Решение |
|-----------|----------|---------|
| **Backend** | Базовый образ `openjdk:11` снят с Docker Hub (`not found`) | Заменён на `eclipse-temurin:11-jdk` |
| **Frontend** | `npm ci` завершался ошибкой из‑за рассинхронизации `package.json` и `package-lock.json`; на Node LTS — ошибки сборки React | Зафиксирован `node:16`, вместо `npm ci` используется `npm install` |

После внесения изменений повторный прогон CI завершился **успешно**. Данный случай демонстрирует практическую ценность CI: расхождение «работает локально / не собирается в чистой среде» выявлено автоматически до этапа развёртывания.

*→ Рис. 7. (опционально) Первый неуспешный прогон CI — для сравнения «до/после» исправления*

### 1.6. Технические детали сборки

**Backend** (`necommerce-backend/Dockerfile`):

- базовый образ: Eclipse Temurin JDK 11;
- сборка: `./gradlew bootJar`;
- запуск: `java -jar necommerce-1.0.jar`, порт **9999**.

**Frontend** (`necommerce-frontend/Dockerfile`):

- многостадийная сборка (*multi-stage build*): стадия `node:16` (сборка React), стадия `nginx` (раздача статики);
- порт контейнера **80**, на стенде проброшен на **8888**.

В workflow включено кэширование слоёв Docker через **GitHub Actions cache** (`cache-from` / `cache-to: type=gha`), что сокращает время повторных сборок backend (Gradle загружает зависимости при первом прогоне 5–15 минут).

### 1.8. Развёртывание на VPS

Для полного закрытия критерия «облачная раскатка» выполнено развёртывание приложения Necommerce на выделенном виртуальном сервере (VPS).

#### Получение доступа

По запросу в рамках дипломной программы получен выделенный VPS с публичным IP-адресом **188.225.74.233**. Доступ организован по протоколу **SSH**: на сервер заранее установлен открытый ключ студента (`ssh-ed25519`), подключение выполняется командой `ssh root@188.225.74.233` без пароля.

#### Установленное ПО и конфигурация

На сервере выполнено:

1. **Docker** и **Docker Compose** — среда контейнеризации для запуска приложения;
2. **Аутентификация в GHCR** (`docker login ghcr.io`) — доступ к опубликованным в GitHub Container Registry образам;
3. **Файл `docker-compose.yml`** в каталоге `/opt/necommerce/` — описание двух сервисов:
   - `backend` — образ `ghcr.io/softm-bot/necommerce-backend:latest`, порт **9999**;
   - `frontend` — образ `ghcr.io/softm-bot/necommerce-frontend:latest`, порт **8888** (проброс на nginx, порт 80 в контейнере).

Образы загружаются из GHCR командой `docker compose pull` и запускаются командой `docker compose up -d`.

При развёртывании выявлена и устранена ошибка production-сборки frontend (отсутствие `REACT_APP_API_URL` в CI): в Dockerfile заданы переменные `REACT_APP_API_URL=/api` и `REACT_APP_MEDIA_URL=/media`, после пересборки образа в GitHub Actions сайт корректно обращается к API через nginx-прокси.

#### Проверка работоспособности

| Проверка | Адрес | Результат |
|----------|-------|-----------|
| Веб-интерфейс (внешний браузер) | http://188.225.74.233:8888 | ✅ Открывается, отображается каталог товаров |
| REST API (напрямую) | http://188.225.74.233:9999/api/products | ✅ HTTP 200, JSON с товарами |
| API через frontend (nginx) | http://188.225.74.233:8888/api/products | ✅ HTTP 200, JSON с товарами |
| Статус контейнеров | `docker compose ps` на VPS | ✅ Оба контейнера Up |

Приложение доступно из внешней сети по публичному IP; SSL-сертификат на данном этапе не требуется — используется протокол HTTP на нестандартных портах **8888** (frontend) и **9999** (backend).

*→ Рис. 7. Работающий сайт Necommerce на VPS (скриншот в браузере по адресу 188.225.74.233:8888)*

#### Вывод по развёртыванию

В результате настройки VPS достигнуто:

- получен и проверен **SSH-доступ** к облачному серверу;
- **установлены** Docker и Docker Compose;
- **развёрнуты** контейнеры backend и frontend из образов **GHCR**;
- **подтверждена** работоспособность стенда: сайт и API отвечают на запросы и **открываются из внешнего браузера**.

Критерий использования облачных сервисов для этапа CI/CD выполнен: цепочка «код на GitHub → сборка в Actions → образы в GHCR → запуск на VPS» работает. Автоматический деплой из пайплайна (job deploy при push) запланирован как дальнейшее улучшение конвейера.
